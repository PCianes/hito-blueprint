# Rules

> Generated by `blueprint/scripts/rules.sh` from `blueprint/rules/` and `custom/`. Do not edit by hand.

## Folders

A folder exists only if (a) deciding whether a note belongs there is a question of fact, or (b) it changes who may write in it. Everything else is told apart with properties, not folders. Folder names are fixed, because rules, scripts and links depend on them; you may add folders of your own if they pass this same test.

| Folder | What goes there | Who writes |
| --- | --- | --- |
| `inbox/` | Anything waiting for a decision | Owner, and anything that captures for them: bots, dictation, agents |
| `goals/` | Vision, focus, values, principles | Owner only; agents read |
| `projects/` | Everything the owner does or maintains, one folder each with its `README.md` | Owner; agents propose |
| `knowledge/` | What the owner knows, in their own words | Owner; agents propose |
| `sources/` | What others say, kept whole | Owner and agents |
| `journal/` | One file per day, `YYYY/YYYY-MM-DD.md`: a folder per year, the full date in the name | Owner; agents propose |
| `encrypted/` | Sensitive material: encrypted on the remote, readable on the owner's machine | Owner; agents propose |
| `archive/` | What is finished and should no longer add noise, at the path it had (`archive/projects/<name>/`); sensitive material stays in `encrypted/` | Owner; agents propose, and read it only when asked |
| `blueprint/` | The shared base: rules, skills, scripts, git hooks | Only where the base is developed; nobody in a copy |
| `custom/` | The owner's changes to the base | Owner; agents propose |
| `.agents/skills/`, `.claude/skills/` | Copies of the skills, generated for each agent | Nobody: `skills.sh` writes them |

Inside each folder the same test applies: a subfolder exists only if placing a note in it is a question of fact, such as a project, the year of a journal day, the author or channel of a source, or one source made of several files. Topics are not facts, so `knowledge/` stays flat; links and each folder's `README.md` organize it.

A project with code keeps here its tasks, decisions and notes. How its code works (running it, testing it, deploying it) goes, briefly, in that repository's own `AGENTS.md`, so any agent working there sees it, even where this repository is not. What holds for several repositories goes where Customizing says.

"Agents propose" means an agent may draft, and the owner decides what stays.

## Type

Every note in the content folders (all of them except `blueprint/` and `custom/`) carries `type` and `created` (`YYYY-MM-DD`) in its frontmatter, and the check fails if either is missing or the type is not one its folder allows. Nothing else until a real query needs it, and no tags: they are mostly topics, which are a matter of opinion, so links group notes instead. Generated files such as `AGENTS.md` and the skill copies are not notes.

- `index`: the `README.md` that presents a folder.
- In `projects/`: `project` has a finish line (a talk, a launch); `area` is maintained with no end (a job, a brand). Things move from one to the other, so this is a property, not a folder. Notes inside a project take its type.
- In `knowledge/`: `knowledge` is what you understood about a subject; `model` holds across subjects, and there are few of them.
- Elsewhere, the folder's kind: `inbox`, `goal`, `source`, `journal`. Notes in `encrypted/` take the type they would have outside it, and notes in `archive/` the type they had before.

Tasks are `- [ ]` items in their project's `README.md`. The journal links to them and never copies them. When work changes a project, update its README.md in the same change: tick what is done, add what came up, and fix what is no longer true. Ticked tasks may be deleted once they no longer help; git keeps them.

## Inbox and sources

`inbox/` holds what is waiting for a decision; `sources/` holds others' material already chosen to keep. These are the only folders where agents write without review: bots, dictation and agents drop anything in the inbox, and agents may store others' material whole in `sources/`. Everywhere else they propose. Processing empties the inbox:

- an idea of yours → a note in `knowledge/` or a task in a project;
- something by others worth keeping → `sources/`, and your view of it in `knowledge/`;
- the rest → deleted.

What you already know you want whole, such as a transcript downloaded on purpose, goes straight to `sources/`.

## Untouched sources

Others' material is never edited, and yours is never copied into it. What you think about a source goes in a `knowledge/` note that links to it.

## Links

Every note is born linked from another (its folder's `README.md`, a project, or another note), except where its path already finds it: a journal day by its date, a source by its author. Use relative Markdown links, never wiki-links, so they work in any viewer and for any agent. The check fails if a relative link points to nothing, so when a note moves (to `archive/`, say), fix the links to it and in it.

## Memory

Agents keep no private memory about the owner or this repository: what they learn goes where every agent can read it and the owner can review it. How the owner wants things done becomes a proposed rule in `custom/rules/my-*.md`; facts go in the note where they belong. If an agent's tool has a memory of its own, turn it off for this repository, or keep in it only what concerns the tool itself.

Before proposing a rule, say when it applies and check that it holds beyond the case that prompted it: what happened once, or only in one kind of task, is not a rule for everything. Scope it to that kind of task, or leave it out.

## Secrets

Secrets (keys, tokens, `.env` files) never enter the repository, not even encrypted. They live outside it, for example in `~/.secrets/`. Keep them out with `.gitignore` (`.env`, `*.env`, `.env.*`, `*.key`, `*.pem`); the check fails if any such file is tracked, wherever it is and whatever `.gitignore` says.

## Sensitive data

Sensitive material goes in `encrypted/`, which git-crypt encrypts on the remote while it stays readable on the owner's machine. Only `encrypted/README.md` stays in clear; the check fails if anything else there is committed unencrypted. Without git there is no encryption at all: keep sensitive material out, or use storage with end-to-end encryption.

Keep only what agents need: whatever an agent reads reaches the model provider, encrypted on the remote or not. Identity and account data (ID numbers, bank accounts, passwords) belong in a password manager; for the rest, a summary beats the whole document. Use neutral file names, because git-crypt does not encrypt names.

## Customizing

`blueprint/` is shared by every copy. Improvements that would help every copy are made in the base itself, where it is developed. That is the repository `hito-blueprint`: working there, read its `DEVELOPING.md` first. Changes for one person never go in `blueprint/`; they go in `custom/`:

- a file in `custom/rules/` with the same name as a base rule replaces it (`custom/rules/links.md` replaces `blueprint/rules/links.md`);
- your own rules are files named `my-*.md` in `custom/rules/`;
- to leave a base rule out, add a line `rules/<name>` to `custom/disable`: the rule stays in `blueprint/`, untouched, but no longer reaches `AGENTS.md`, and updates cannot bring it back;
- rules that hold in every folder, not only in this repository, are files named `my-*.md` in `custom/global/rules/`, and such skills are folders named `my-*` in `custom/global/skills/`. They go in `GLOBAL.md`, which `blueprint/scripts/global.sh` takes to each agent outside the repository, and also at the end of `AGENTS.md`, so they hold here even where `global.sh` has not run. Where a rule or skill goes depends on where it applies: only in this repository, in `custom/rules/` or `custom/skills/`; only in another repository, in that repository's own `AGENTS.md` and skills, never in `custom/global/`, which loads in every session everywhere; in any folder, in `custom/global/`. Within `custom/global/`, a rule is for what every session needs (how to answer, how to commit), and a skill for what is needed only when doing something specific (writing React components, say): a rule is read whole in every session, while a skill takes only its name and description until it is needed.

Besides rules, `custom/skills/` holds the owner's skills (see Skills), a file in `custom/templates/` replaces the base template with its name in `blueprint/templates/` (`journal.md` is the one for each day's note, which `blueprint/scripts/today.sh` creates), `custom/git-hooks/commit-msg`, if present, is run with the commit message and can reject it, and `custom/git-hooks/test-*.sh` run with the other tests. Anything else in `custom/` makes the check fail. `AGENTS.md` and `GLOBAL.md` are generated by `blueprint/scripts/rules.sh`. Never edit them by hand.

## Skills

A skill is a procedure an agent follows: a folder with a `SKILL.md` whose frontmatter has `name` (equal to the folder name) and `description` (when to use it), plus any scripts it needs. Common skills live in `blueprint/skills/`, the owner's in `custom/skills/`: a custom skill with the name of a base one replaces it, the owner's own are named `my-*`, and a line `skills/<name>` in `custom/disable` leaves a base one out, untouched in `blueprint/` but no longer copied for the agents. `blueprint/scripts/skills.sh` copies the result to `.agents/skills/` and `.claude/skills/`, where agents look for them. Never edit those copies.

Write skills for the weakest model that will run them: plain steps, scripts in `sh`, and no tool names of any one agent.

When an agent finishes a task that is likely to come back and would take the same steps again, it proposes turning it into a skill in `custom/skills/my-*`, and writes it only once the owner agrees.
